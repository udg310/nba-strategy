## 1. 雷霆场为什么需要逐单追踪

2026-11-14 雷霆对快船，比赛 ID 为 `401909304`。北京时间 13:20:02.196，D 通道在雷霆领先 5 分、卖一 0.76 时发出 3.73 美元的买入信号。13:20:09.124，本地写下一条买入记录，`tries=2`、入账价 0.73、5.109588 股。终场日志仍持有 5.109588 股，赛后复盘记录实际约 10.22 股。约 6.93 秒是信号到本地记账的时间。现存日志缺少两张可逐笔比对的交易所订单号，重建每次 POST、受理、撮合和可见的先后仍需账户订单与成交导出。[单场事件记录](../data/live_trade_final/2026-11-14/032315/events.jsonl) · [赛后复盘](strategy_current_20261114.md)

另有一个独立的离线复现场景。原评审在旧执行脚本版本 `6fb4cde` 中让模拟场所受理首单，随后持续返回空成交列表和零余额。第 16 秒后再输入比分变化，旧 D 信号再次命中，依次出现 `signal → buy_posted(stub-1) → buy_gave_up → signal → buy_posted(stub-2)`。这个反例解释了为何不能用本地等待到期释放开仓机会。旧脚本只读当天 JSONL 恢复已记账结果，跨日和未记账委托可能漏查。成交查询出错可能被当成空列表，同标的成交可能被错记到其他订单。卖单结果不明超过 30 秒时，旧脚本还可能按余额重发。旧脚本的 SDK 写重试也需随执行入口切换一并退出。[旧脚本](../scripts/live_runner.py) · [旧脚本回归用例](../scripts/test_live_runner.py)

## 2. 受理、预算与身份

`executor.py --scoreboard` 在一个 Python 进程内读取比分和盘口、运行 A/C/D 策略、执行委托并提供本机 API。策略也可作为独立进程通过 HTTP 使用同一执行器。上游负责比赛映射、入场条件、退出原因和机会截止时间。后端依据请求期限裁决能否发送，检查风险与可执行报价，签名、提交并核对实际成交。交易写权限只交给该账户唯一的执行进程。[启动入口](../scripts/executor.py) · [策略生产者](../scripts/executor_producer.py)

| 对象 | 当前契约 |
| --- | --- |
| 开仓意图 | 一个账户和环境内，每场比赛每个 A/C/D 通道最多一个 `OPEN`。A 与 C 可以选择同一标的。重复请求沿用首次的比赛、标的、市场、预算、限价和截止时间。同键改标的、市场、预算或限价返回 409。报价变化和进程重启均不能产生第二个开仓名额。 |
| 退出意图 | 用开仓意图的 ID 作为 `position_id`，每个仓位至多一个 `CLOSE`。首次要求开仓已核实终态，数量等于本仓已确认量。止盈、时间到期、强平或 D 分差止损都沿用该仓的退出意图。旧尝试未决时保留预留。终态后可按已核实余量延续同一意图，新的有效退出信号可更新限价和期限。 |
| 尝试与成交 | 在单账户账本中，`(intent_id, number)` 唯一，同时最多一个可能成交的尝试，每个非空交易所订单号只能绑定一次。已确认明细以 `(order_id, id)` 唯一，实盘明细 ID 为交易哈希和日志序号。重复观测复用原分录，金额或身份矛盾使该笔事务回滚。 |
| 金额与名额 | 预算、现金、费用、价格、份额均以百万分之一为整数单位。开仓的 `amount` 为美元预算，平仓的 `amount` 为股数。`READY` 与预留、业务键和首个审计事件在同一事务提交。检查可用现金和 `--max-open`，未决买单计入名额与资金。开仓意图累计确认的股数才可用作卖出依据。 |

生产者首次构造请求时，开仓默认 15 秒、平仓默认 900 秒，以 Unix 毫秒写入 `signal_at` 和 `deadline`，并在决策日志保留请求。外部调用方可提供自己的期限。重发开仓请求沿用原截止时间。到期未发的开仓应释放预留。已取得发送权的旧单继续跨日查证。调度受阻时及时清理过期 `READY` 仍是第 6 节的待办。[账本及风险检查](../scripts/executor_ledger.py) · [唯一约束](../scripts/executor_schema.sql)

## 3. 一次提交、恢复与记账

1. **抢占发送权。** 工作者在 SQLite 事务内重查期限与风控，从 `READY` 建立尝试并记为 `SUBMITTING`。事务提交后才调用场所。实盘再查市场与标的、盘口、有效价、手续费、余额及授权，生成签名订单，将本地订单哈希与加密签名载荷写入 `live_prepared`，提交后才允许传输。凭证和可重放载荷不得写入日志。
2. **每次尝试单次 POST。** 适配器使用固定 SDK、关闭 SDK 写重试，发送前复核期限与停机标志。传输后超时、回执含糊或订单号冲突按可能送达处置，只按原身份查询。部署代理、交易所字段和实际账户的身份匹配仍需验证。今后如引入重放，须先证明目标协议对同一原始签名载荷只生成一张可执行订单。
3. **按证据释放预留。** 明确发生在传输前的失败、可验证的零成交拒绝、终态且累计量和明细相符的零成交可以结束尝试。可重试的首次零成交在原窗口内最多增加一次自动尝试，永久参数问题终止。404、断线、空列表、余额无变化、单独撤单回执或窗口到期均不足以证明零成交。
4. **拆分成交逐条入账。** 有订单身份的受理记 `ACCEPTED`。无可靠回执通常记 `UNKNOWN`。读失败保留已有状态。部分明细确认后逐笔入账，剩余额度继续预留。用已见匹配量的历史最大值抵抗旧回报，终态累计量须与已确认明细及该最大值一致。开仓确认有成交后结束，不自动补足预算。平仓终态有余量可继续处理。账本以成本、费用、确认量重算仓位和可用额。[工作循环](../scripts/executor_engine.py) · [场所适配](../scripts/executor_venues.py) · [签名、发送与查单](../scripts/executor_clob.py)

**恢复。** 启动扫描全部日期的未决意图，把遗留 `SUBMITTING` 转入 `UNKNOWN`，先查账户成交与已有尝试。已抢占但尚未持久化签名身份即宕机，允许交易所实际零张订单，本地仍冻结等候证据。账户成交按页保存，实盘固定分页结束时间并重叠回读 5 分钟，同页明细与游标一同提交。已确认外部成交找不到订单归属时，阻挡新开仓及同标的的新平仓，允许其余可核实的处置。账户成交同步失败或超过 30 秒未刷新，后台暂缓所有 `READY` 的发送。启动对账报错会记录日志，健康接口仍可就绪。单笔查单失败与全账户成交同步失败的影响范围不同。

**运行与值班。** 账本绑定账户、环境和初始资金，位于本机磁盘，启用 WAL、外键和 `synchronous=FULL`。进程内以一条连接、互斥锁和短事务处理账本操作。SQLite 锁等待为 3 秒，场所网络请求在事务外。数据库不能提交发送权时不发新单。同一主机、系统用户和环境按账户取得操作系统独占锁，重启继续使用同一路径。另一个系统用户、另一台机器或绕开锁的程序，须在部署交接时另行排除。[账本](../scripts/executor_ledger.py) · [账户锁](../scripts/executor_lock.py)

## 4. 后端接口与观测

默认监听 `127.0.0.1:8787`。除 `GET /healthz` 外，HTTP 请求需带 `Authorization: Bearer <token>`。实盘环境显式配置令牌。只读对账指对场所不提交委托，拉到的新证据仍会更新本地账本。[接口与鉴权](../scripts/executor_api.py) · [查询与复核实现](../scripts/executor_reports.py)

| 接口 | 语义与值班检查 |
| --- | --- |
| `POST /v1/order-intents` | 接收 `account, environment, game_id, channel, action, asset, market, amount, limit_price, signal_at, deadline`，另有 `reason`，平仓需 `position_id`。账户和环境可取服务默认值。首次本地受理返回 201，等价重放 200 和同一 ID，同键冲突或风控拒绝 409，参数格式错误 400。同步响应只代表账本受理。 |
| `GET /v1/order-intents/{id}`、`GET /v1/orders/{orderID}/trace` | 意图详情含尝试、订单号、确认量、预留、关联仓位、`last_check` 及时间线。活跃订单的 `next_check_estimate` 只是估算。订单号可反查事件与交易所观测明细。 |
| `POST /v1/reconcile`、`GET /v1/account` | 主动拉取账户成交与已有订单，复算报告。账户接口返回本地可用现金。启动和人工查核不能产生新的交易所委托。 |
| `POST /v1/account/pause-open`、`POST /v1/account/resume-open` | 持久暂停或恢复开仓。暂停后仍跟踪旧尝试，允许风险条件满足的已知仓位退出。停机移交还需停用旧写方的交易权限。 |
| `GET /v1/review/fills`、`POST /v1/review/resolve`、`GET /v1/review/actions` | 核对未归属明细。凭证据和操作人执行 `bind` 绑定原订单、`import` 补录已确认明细、`manual` 标记手工单、`zero` 结束有零成交证据的未知尝试。记录处置前后状态，告警超时继续保留冻结。 |
| `GET /v1/metrics` | 重复及冲突请求数（随进程重启重置）、未知尝试数量与最老年龄、30 秒提示和 5 分钟人工复核阈值、未归属数、从尝试创建到入账事件的最大延迟。未归属成交和报告数量差额可触发日志告警。外部重复单仍须通过账户明细检查。 |
| `POST /v1/settlements` | 对已核实的 D 仓位提交 `position_id, venue_event, leg_id, shares, payout, fee, confirmed, actor, evidence`，须覆盖已确认且未预留的实际剩余份额。相同凭据重复登记不会重复计款。比赛终场只触发报告，兑付另需凭据。 |

**部分实现 · 账户余额与报告差额。** 实盘准备单笔委托时会检查交易所余额和授权，账户成交读取也能发现未归属明细。目前缺少把外部现金和各标的余额与账本持仓、预留定期交叉核对的流程，接管时须逐项核清。单场报告逐意图比较数量、金额及费用，有差异即标为 `PENDING`。自动报告差额告警只统计全场买入或卖出总股数有差额的比赛。若仅费用或成交金额不同，或 A、C 的同方向数量差刚好抵消，报告可待核而这项告警保持静默。验收应分别注入纯费用差和通道间相抵的数量差，核对报告字段、状态及告警结果。

**待验证。** 按目标环境核对读错误、无记录、明确零成交的分类，验证同一开仓意图有两张可能成交的外单时值班人员能否立即收到通知。当前指标给出本地尝试到成交事件的时延。单独衡量场所受理到首次可见的延迟还需保留相应时间戳。

## 6. 两项可独立排期的后端需求

### 6.1 平仓零头与名额释放

**当前缺口。** 实盘卖出按 0.01 股向下取整，模拟场所按请求份额撮合。账本按已确认买量大于卖量且尚未兑付来计算持仓占位。若买入 5.109588 股并确认卖出 5.10 股，实际仍持有 0.009588 股。现有逻辑可能为这笔余量建立下一次尝试，在精度检查处被拒绝，名额继续占用。[卖出精度](../scripts/executor_clob.py) · [模拟场所](../scripts/executor_venues.py) · [额度与退出尝试](../scripts/executor_ledger.py)

**交付条件。** 每个仓位按整数微股单独计算实际余量，从已确认买入量中扣除已确认卖出量和已核实兑付量。当前步长为 10,000 微股，可自动卖出量为 `(余量 // 步长) × 步长`，实盘准备、账本与模拟验收需共用该精度。前一尝试已核实且仍有整步时，沿用同一退出意图，只卖可卖量。开仓及所有卖出尝试均已核实终态、没有影响本仓的待核成交、退出仅剩正零头时，在同一事务内登记结束原因、释放卖出预留和名额、写审计事件。保留原目标、真实余量、经济敞口和所属通道。现金、成交及盈亏只能随真实成交或兑付变化。盘口无买盘、价格受限、余额暂缺、未知委托和明细不齐须各有可查原因。重复退出与重启复用原处置，按场报告并列实际余量、可自动卖出量和结束原因。

| 经订单 API 构造的输入 | 必须观察到的结果 |
| --- | --- |
| 买入 5.109588 股，退出并确认卖出 5.10 股。重复平仓 10 次，再重启重试。名额上限 1 | 外部卖单共 1 笔，无新增尝试。已卖 5.10、实际余 0.009588、可自动卖 0。另一场符合风控的开仓能占用名额。 |
| 分别构造终态余量 0、0.009999、0.010000、0.019588 股 | 依次为已清仓、纯零头、可卖 0.01、可卖 0.01。最后一组的整步卖出确认后，真实零头为 0.009588。 |
| A 与 C 持有同一标的且各有零头。另设卖单回执丢失或仅部分明细可见 | A/C 零头独立归属。未决仓位继续核查并保留名额。最终累计量与明细核对一致后才可结束。D 仓位保留凭证兑付路径。 |

### 6.2 查单退避与发单调度

**当前缺口。** 后台每 500 毫秒检查队列，按 `last_check, id` 排序，最多四个订单任务并行。快速查单失败不推进该排序时间，旧单可反复被选中。若四次查询都挂起，可占满四个工作位直到各自 30 秒的实盘查询期限，而新开仓通常只有 15 秒。账户成交另有独立读取容量。手工对账有自己的并发循环，订单详情尚未返回真实排期。[后台调度](../scripts/executor_engine.py) · [订单与账户读取容量](../scripts/executor_venues.py)

**交付条件。** 按当前尝试持久化连续读失败次数、最近检查、下次可查时间与失败原因。建议第 1–6 次依次退避 1、2、4、8、16、30 秒，之后保持 30 秒，成功读取后回到正常频率。404、超时、临时读错只改变查询计划，保留身份、已见状态、发送次数和预留。告警从原尝试开始计龄。建议四个工作位中常规查单至多占三个，给到期可发送任务留位。新单持续积压时也要公平安排到期查单。受风控阻挡的 `READY` 应延后复查，未发送且已过期的意图及时清理。

后台、启动恢复与人工只读对账须协调同一尝试的查询权，迟到的失败结果不能覆盖新成功或终态。重启恢复下次查询时间，旧库缺该字段时首次视为可查。订单详情应提供真实排期及最近读错。调度继续遵守账户成交同步新鲜度、资金、授权与风险门槛。

| 驱动正常后台循环的输入 | 必须观察到的结果 |
| --- | --- |
| 四张旧单持续 404，账户成交同步正常。加入另一个标的、资金充足的新开仓 | 新单在 15 秒内开始提交。四张旧单依退避计划复查，各自新增外部 POST 为 0。 |
| 四个查询一直挂起，分两次独立运行加入一笔合格开仓或另一场的合格平仓，无其他发单积压 | 两组均在随后两个 500 毫秒周期内开始处理新单。另持续加入新单，到期查单也能获得工作位。记录首次发送及每次查单开始时间。 |
| 连续两次读失败后重启，随后成功取得迟到成交，再触发一次人工对账 | 恢复原重试时间。成功后失败数清零。只记一笔成交，人工对账新增外部 POST 为 0。 |
| 账户成交同步失效，或新请求受资金限制 | 继续到期清理及只读查询，拦住新发送。恢复后只发送仍有效且通过风控的意图。 |

两项升级都要用含一张未知订单和一笔部分卖出仓位的旧账本验证。逐项比对订单身份、现金、份额和预留，仅给证据完备的仓位补录零头处置。重提已到期的未发开仓，外部 POST 为 0。重放已发但回执未知的请求，新增 POST 也为 0，原订单继续核查。

## 8. 启动、切换与回退

1. **本机开发与升级。** 模拟盘使用 Python 3.12 标准库，在仓库根目录执行 `python scripts/executor.py` 启动服务，或加 `--scoreboard` 一起启动策略。首次创建 `var/executor/paper.db`，没有比赛也可就绪。用 `python scripts/executor.py --recording data/live9_20261114.json` 检查九场离线录制。开发、测试和实盘分别用独立账本。版本变化与代码一同提交，验证空库初始化、带数据升级、失败回滚和重启。运行中备份须覆盖已提交的 WAL，使用 SQLite 在线备份或在所有写方关闭后复制完整数据库。[运行说明](../README.zh-CN.md) · [三平台 CI 定义](../.github/workflows/executor.yml)
2. **离线放行。** 对齐固定比分和盘口下的策略意图，执行第 7 节。两项后续改动交付时另执行第 6 节。按目标 SDK、钱包模式、Polygon 链和实际市场版本核对签名域、离线哈希、费用与精度、最终性、查单字段、分页回读、拒绝分类以及部署代理的写重试。缺少可验证订单身份的未知尝试保持冻结。
3. **影子运行。** 保留账户原有的唯一写方，用独立模拟账本接收相同信号，逐场比对规范比赛 ID、通道、标的、方向、报价和拟用预算。用只读账户证据核对差异，验证影子实例的交易所下单数为 0。模拟场所的零费用与限价成交不能代替实盘成交样本。
4. **切换单一写方。** 暂停新开仓，停用旧执行脚本的写权限。清点开放订单、未决尝试、资金、仓位与已占通道，按订单及成交凭据核对历史。无法归属的单独隔离。账户探测并不完成历史持仓导入。使用核对过的固定实盘账本或独立空仓账户，显式指定 `--account`、`--db`、`--capital`，首次以 `--init-live` 建库，日后复用原文件。小范围接管，对账无未解释差额后扩大。[实盘配置与命令](../README.zh-CN.md#实盘接入与切换)
5. **回退与扩容。** 暂停开仓，并在移交前关闭全部新委托的发送权限，继续消费回报和查单。导出未决订单、已用通道、真实余量及预留。仅在接替方能正确恢复且原写方已失去发送权后移交。证据不足时保持只读对账。回退演练需覆盖中途崩溃，证明同一账户始终只有一个有效写方。增加比赛或策略进程时先复用原服务并观测锁等待。只有本地短事务仍挤占入场窗口，或需要跨主机写入与接管时，再评估共享数据库及跨主机发送权。
