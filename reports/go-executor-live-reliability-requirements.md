# NBA 订单执行后端需求：平仓零头与查单调度

**待排期 · 2026-11-14**　评审基线为 `e397a54`。两项需求由执行后端独立交付，涉及 Go 服务、SQLite 账本和交易所适配器。可用已构造的订单意图和模拟交易所完成验收。[执行后端原始需求](go-order-execution-requirements.md)

| 后端事项 | 完成标准 |
| --- | --- |
| 平仓零头 | 可卖份额全部确认卖出后，账本保留真实零头、释放并发持仓名额。调用方重复平仓时复用已有结果 |
| 查单调度 | 连续失败或挂起的查询按计划重试。账户对账正常且风控通过时，其他比赛的订单仍有机会在截止前发送 |

**与策略端的接口约定。** 上游负责判断交易机会，并在开仓意图中提供 `signal_at` 和 `deadline`。执行服务保存首次受理的截止时间，重复提交沿用原值。达到截止时间时，尚未发送的买单停止发送，可能已经送达的订单继续按原订单身份对账。后端以请求载明的截止时间验收。比分和入场条件由策略侧评估。[账本受理与发送权](../internal/executor/ledger.go) · [发送前期限检查](../scripts/executor_clob.py)

## 1. 平仓零头的记账与名额释放

**已复现的场景。** 持仓为 5.109588 股，按当前实盘卖出精度可卖 5.10 股。卖出确认后还剩 0.009588 股，适配器会因数量取整为零而拒绝，调用方再次发起平仓时，执行服务可能为同一零头重新创建尝试。相关路径见[卖出数量处理](../scripts/executor_clob.py)、[账本与名额计算](../internal/executor/ledger.go)及[成交入账](../internal/executor/ledger_fills.go)。

**数量口径。** 以百万分之一股的整数运算。对同一仓位，实际余量等于已确认买入量减已确认卖出量、再减已核实兑付量。按当前适配器的卖出步长 10,000 微股，`可卖量 = (实际余量整除步长) × 步长`。例如余量 19,588 微股，下一笔可卖 10,000 微股，待卖出确认后才可把余下的 9,588 微股标记为零头。精度规则应与实盘适配器共用同一口径，并在模拟场所覆盖该规则。

| 账本证据 | 执行动作 | 账务与名额 |
| --- | --- | --- |
| 有退出需求，余量至少一个步长，前一尝试的最终成交已核实 | 沿用同一退出意图，仅发送该仓位的可卖量 | 保留原始退出目标、实际已卖量和真实余量 |
| 开仓及所有卖出尝试均已核实终态，退出时只剩正数零头，也没有影响该仓位的待核成交 | Go 一次事务记录“自动退出结束，剩余零头”、释放卖出预留并追加审计事件 | 释放并发持仓名额，按原仓位保留零头及其经济敞口。成交、现金和盈亏只随真实成交或兑付变动 |
| 仍有未知委托、未确认成交或归属差异 | 继续按原订单核查 | 保留相关预留和名额。余额暂缺、无买盘、价格受限也须分别记录原因 |

执行服务的自动重试、重复平仓请求和名额计算共用同一仓位处置结果。即使调用方继续请求平仓，接口也返回原结果，新增卖出尝试为零。按比赛查询时，同时显示实际余量、可自动卖出量和结束原因。报告仍按真实成交核对差额。D 持仓继续按已有凭据登记兑付，A/C 共用同一标的时各自保留零头归属。重启和重复请求都复用原处置记录。[赛后报告](../internal/executor/report.go) · [兑付登记](../internal/executor/ledger_settlement.go)

| 验收输入 | 可观测结果 |
| --- | --- |
| 开仓 5.109588 股，发起退出，交易所确认卖出 5.10 股。再提交十次相同平仓请求并重启后重试 | 外部卖单共 1 笔，卖出记账 5.10 股，持仓仍列 0.009588 股，可自动卖出量为 0，无新增尝试。将名额上限设为 1，另一场合格开仓可被受理 |
| 分别构造 0、0.009999、0.010000 和 0.019588 股的已核实余量 | 依次得到已清仓、纯零头、可卖 0.01、可卖 0.01。最后一组卖出确认后报告余 0.009588 |
| 同一标的的 A、C 各有零头。另构造卖单回执丢失、仅部分明细可见的仓位 | A、C 分开记账。对未知卖单继续查证，直到最终累计量与明细一致才允许释放名额 |

## 2. 查单退避与发单调度

**现有故障路径。** 后台按 `last_check` 从早到晚取未决意图，最多并发四个。查单失败时直接返回，失败项保留最早的排序时间。四张旧单既可能因快速失败被反复选中，也可能同时等待各自的 30 秒超时，超过新开仓的整个 15 秒窗口。[工作循环](../internal/executor/engine.go) · [未决队列](../internal/executor/ledger.go)

1. **让失败查询晚些再试。** 按委托尝试保存连续读取失败次数、最近查询时间和下次允许查询时间。建议初值为失败后等待 1、2、4、8、16、30 秒，后续维持 30 秒。成功读取后恢复正常频率。404、超时和临时读错误只更新查询计划，原订单身份、发送次数、状态与预留由成交证据决定。未知订单告警的年龄仍从原尝试开始计算。
2. **限制占位。** 在现有四个订单工作位内，建议后台查单最多同时占三个，给可发订单留一个位置。持续有发单积压时也应让到期查单取得工作位。到期任务按等待时间公平轮转。对于受风控阻挡的 READY 请求，安排下次检查，避免同一批受阻订单反复占用发单位置。已过期的未发送意图应及时释放预留。
3. **并发与恢复。** 调度结果按当前尝试 ID 更新，同一尝试同时最多执行一次查单，迟到的失败结果不能覆盖更新的成功或终态。重启恢复下次查询时间，旧库缺字段的未决订单首次视为可查。启动恢复和人工“立即对账”只读，使用同一并发限制。常规工作循环仍须满足现有账户对账新鲜度及资金条件才允许发单。订单详情返回真实的下次查询时间和最近失败原因。

| 验收输入 | 可观测结果 |
| --- | --- |
| 四张旧单反复返回 404。账户成交读取正常，另一个标的有资金充足的新开仓 | 新开仓在 15 秒窗口内开始提交。每张旧单依退避表再次查询，对旧单的新增外部 POST 为 0 |
| 四张旧单的查询一直挂起。在第一轮查询尚未返回时，分别加入一笔合格开仓、一笔其他比赛的合格平仓，两组独立运行且无其他发单积压 | 两组都在随后两个 500 毫秒调度周期内开始处理新单，无需等待 30 秒超时。反向持续加入新单，到期查单也取得工作位 |
| 查询连续失败两次后重启，随后成功取得迟到成交，再人工触发一次对账 | 后台沿用原重试时间，读成功后清除连续失败次数。成交仅入账一次，人工对账新增 POST 为 0 |
| 账户成交同步已失效，或新请求受资金限制 | 调度仍执行到期清理和只读查单，发单保护生效。恢复后只有仍在有效期且通过风控的请求可以发送 |

## 后端验收方式

两项需求可独立排期。测试使用可控时钟、临时 SQLite 文件和能记录每次发单的模拟交易所。零头用例应通过订单 API 提交开平仓，检查外部卖单数、实际余量和下一笔开仓能否占用名额。调度用例应驱动正常后台循环，同时记录查单开始时间和其他订单的首次发送时间。

升级测试使用已有账本，包含一张未知订单和一笔已部分卖出的仓位。迁移后仅对证据完备的仓位补记零头处置，逐项核对订单标识、现金、持仓和预留。截止时间作为接口回归项：提交一笔已到期的开仓请求，外部发单数应为零。重放一笔已发出但回执未知的请求，新增发单数应为零，原订单应继续对账。
