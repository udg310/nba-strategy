# NBA 实盘交易执行后端需求文档

**评审稿 · 2026-11-14 · 单机 Go 执行服务 + SQLite**

首版只迁移交易执行。现有 Python 继续生成 A/C/D 信号并运行回测，一个 Go 进程负责同一账户的委托和对账，SQLite 在本机保存订单簿。策略只表达交易意图，包含账户、比赛 ID、策略通道、方向和预算。服务负责把这个决定落实成可追溯的订单，并持续查清结果。重复比分、请求超时、进程重启和迟到的成交，均须归回同一个意图。结果暂时查不清时，接受错过入场，保留资金占用和订单跟踪。

| --- | --- | --- |
| 13:20:02.196 | D 信号，雷霆领先 5 分，卖一 0.76，预算 3.73 美元 | 对应一次开仓决策 |
| 13:20:09.124 | 脚本写入一条买入记录，`tries=2`，5.109588 股，入账价 0.73 | 约 6.93 秒是从信号到本地记账的耗时。尝试计数无法独立证明两笔委托各自成交 |

**当前版本仍能复现另一条明确的重复路径。** 在提交 `6fb4cde` 上，以模拟交易所受理第一单，让成交列表持续为空、余额持续为零。第 16 秒驱动执行循环，随后输入新的比分变化，原 D 信号仍可从比赛历史中命中。实际观察到 `signal → buy_posted(stub-1) → buy_gave_up → signal → buy_posted(stub-2)`。同场同通道共提交两次，复现全程未连接交易账户。现有测试仅在提交后第 3 秒检查未重发，第 6 秒就提供了成交。[执行逻辑](../scripts/live_runner.py) · [现有回归测试](../scripts/test_live_runner.py)

| 当前实现 | 需要覆盖的故障 |
| --- | --- |
| 买入用内存中的 `posted/pending/done` 去重，15 秒到期可移除等待标记 | 入场机会可以过期，已发订单可能稍后成交。重启、跨日、双实例也会丢失内存互斥 |
| 启动只扫描当天 JSONL 中的买卖结果；SDK 配有 `retry_on_error=True` | 已发送但尚未记账的单可能漏恢复；应用、SDK 和代理的写请求重试都要核实 |
| 成交查询异常返回空列表，订单 ID 不匹配时可按时间和同一标的宽松归属 | 查失败、无记录和确认零成交需要分别处理；A、C 同标的以及手工交易可能被错记 |
| 卖单结果未知超过 30 秒时可能凭余额重新发送；卖出循环可阻塞该场处理 | 卖出也需要持久化幂等和份额预留。退出理由变化、迟到成交均可能触发重复卖出 |

## 2　业务约束与服务边界

- **开仓次数。** 沿用当前策略，每个实盘账户、每场比赛、每个策略通道最多完成一次开仓。同一笔决策允许产生多个成交明细。A 与 C 可以各开一次，即使两者买的是同一标的。任何可能已被受理的尝试均阻止创建下一笔委托。
- **退出份额。** 一个策略仓位只有一个同时生效的退出意图。止盈、时间退出和强平同时命中时，归回同一退出计划并记录原因。累计卖出量加仍可能成交的预留量不得超过该仓位的已确认可卖量。
- **执行范围。** 报价、资金和持仓检查、签名、提交、回报处理、账本、对账与恢复均由 Go 服务负责。首期复用 Python 的 A/C/D 信号作为生产者和回放基准。原实盘入口中的买卖副作用随切换关闭。策略迁移到 Go 可独立验收。
- **进程间协作。** 同机可以运行多个策略进程，它们通过本地 HTTP 接口提交意图，使用同一个 Go 执行服务。交易凭证只交给执行服务。实盘部署为每个账户配置唯一的账本路径和执行入口，服务启动先取得该账户的操作系统独占锁，持有至进程退出。重复启动在发单前退出；接替进程取得锁后先恢复未决订单。
- **进程内并发。** 用有限数量的 goroutine 并行处理不同比赛的报价、提交回执与成交查询。一次查单等待网络时，其他比赛仍可前进。goroutine 共享所属进程的内存，进程重启和跨进程重复请求的去重依据保存在账本里。并发数受交易所限频约束，积压的入场请求先检查是否过期。[Go 对 goroutine 的说明](https://go.dev/tour/concurrency/1)
- **SQLite 写入。** 账本放在执行服务主机的本地磁盘，启用 WAL。服务内用一个写连接顺序提交短事务，可用独立读连接查单。网络请求在事务外执行，有限等待后仍遇锁忙则保留原状态、稍后重试本地操作。WAL 允许读写并行，同一时刻只有一个写事务。[SQLite WAL](https://sqlite.org/wal.html)

## 3　P0 幂等协议

### 3.1 先确定哪两次请求属于同一笔交易

| 对象 | 持久化标识或约束 | 冲突时的行为 |
| --- | --- | --- |
| 开仓意图 | 唯一键 `(账户, 环境, 规范比赛ID, 通道, OPEN)`。策略版本、比赛时间、报价、实例 ID 只作审计 | 相同业务请求返回已有意图与状态；同键换标的、方向或原始预算，返回冲突，保留原决定。生产者重试使用首次冻结的参数 |
| 退出意图 | 当前策略按 `(position_id, CLOSE)` 唯一；退出原因作为事件 | 复用已有意图；终态部分成交经核实后，仅可继续处理剩余份额 |
| 委托尝试 | 唯一 `(intent_id, attempt_no)`；每个意图最多一个尚可能成交的尝试；交易所订单 ID 按账户与场所唯一 | 重复任务读取原尝试。旧尝试尚有成交可能时，禁止重签或创建下一尝试 |
| 成交记账 | 以场所、账户、订单和稳定成交明细 ID 唯一；一条交易含多条己方执行明细时采用可验证的明细标识 | 重复或乱序回报只推进已验证状态，同一经济成交仅产生一次持仓与资金变动；缺少可靠归属的明细进入待核对队列 |

建立意图时，在同一事务中写入原始参数、锁定账户风险额度、预留买入预算或可卖份额、占用开仓名额，将意图置为可扫描的 `READY` 状态。以唯一约束裁决并发请求，失败整体回滚。金额、价格、份额使用定点整数或精确十进制，单位和交易所舍入规则显式记录。未决买单计入资金和持仓上限。

### 3.2 发单前后可能宕机时如何处理

1. 工作者先持久化不可变委托参数、签名所需身份以及可验证的本地订单标识。若该协议支持离线生成交易所订单哈希，保存哈希与加密签名载荷。数据库提交成功后，采用带版本条件的状态更新抢占一次发送权，先记 `SUBMITTING`，再发出 POST。凭证及可重放载荷不得写入应用日志。
2. 关闭交易写路径上 SDK、HTTP 中间件及代理的隐式重新发单。服务直接扫描 SQLite 中可发送的记录。多个 goroutine 发现同一条时，只有成功将状态从 `READY` 更新为 `SUBMITTING` 的工作者获得发送权，其余读取已有状态。
3. 保留受理回执、订单 ID、响应分类和时间。超时、断连、含糊的错误、落库前宕机，以及发现遗留 `SUBMITTING`，都按“可能已送达”接管。即使事实上是发包前宕机，也允许错失该单。数据库与交易所之间没有共同提交点。
4. 初版对结果未知的尝试只查单。未来若要自动重放，须针对实际部署的交易所协议证明“同一签名载荷重复提交只产生一个可执行订单”，并验证身份计算与查询；重放必须使用原载荷。自定义 HTTP 幂等头只约束自己的服务，不能当作交易所去重能力。

### 3.3 状态迁移与重试判据

| 已取得的证据 | 本地处置 | 是否允许新委托 |
| --- | --- | --- |
| `READY`，尚未取得发送权 | 到期可标 `EXPIRED_UNSENT` 并释放预留；有效期内可抢占发送 | 只允许当前尝试的首次提交 |
| `SUBMITTING` 后无可靠回执，或返回超时、结果未知、查单 404、空成交列表 | 记 `UNKNOWN`，保留占用；继续按原身份查询。读错误单独计数 | 否 |
| 交易所已受理、延迟撮合、已匹配但尚未最终确认 | 记 `ACCEPTED` 或待确认成交，关联订单和各笔明细；保持相应预留 | 否 |
| 部分明细已最终确认 | 按明细增量记账；未知余量继续预留。FOK 的多条成交回报也可能分批可见 | 旧单终态与最终成交总量核实前，否 |
| 明确拒绝且证明零成交，或终态取消且已核实零成交 | 记录交易所证据；永久参数错误终止。暂时性且可重试的失败仅在原入场窗口内重新检查价格、额度和预算 | 允许同一意图的受限新尝试，默认最多一次额外尝试 |
| 全部成交，或已核实终态累计成交量且部分成交 | 以最终成交明细及费用结清预留。开仓意图有成交即消耗该场通道机会；退出意图可按已核实余量继续卖出 | 开仓不自动补量；退出仅限真实余量 |

15 秒入场窗口只界定还能否开始一笔新的买入尝试。查询周期、报警阈值和交易机会期限各自独立。撤单请求与到期通知也可能和成交交错，只有核实最终累计成交及明细后才能释放相应资源。

## 4　P0 对账与恢复

**归属与入账。** 首版定时查未决订单并分页拉取账户成交，以订单 ID 或经验证的订单哈希归属到尝试。保存游标并重叠回读；游标推进须在对应事件持久化之后。首次看到匹配即记录待确认敞口，最终确认后，在一个事务内插入成交分录、更新策略仓位、核销预留并追加审计事件。状态倒序到达不得回退已确认分录。订单侧累计量大于成交明细合计时保持差额待核，继续拉取。Polymarket 提供账户订单与成交通知，实际市场版本的字段、状态及分页行为须通过适配器契约测试。[订单提交](https://docs.polymarket.com/trading/place-orders) · [账户实时回报](https://docs.polymarket.com/trading/realtime-order-updates)

**恢复与隔离。** 服务启动时跨日期扫描全部未决意图、未归属成交和有份额的仓位。按账户完成订单、成交与预留核对后再开放受影响范围的发单。用资产余额做总量交叉检查；同一标的可包含 A、C 和账户手工交易。缺少精确归属时保留原始回报、冻结相关额度或份额、告警，不按时间接近或余额变化猜测订单。数据库不可写时暂停发单，恢复后先补拉回报。

**值班处置。** 提供按比赛、通道、意图和交易所订单 ID 查询的订单时间线。人工复核可关联有凭据的外部订单、补录唯一成交或附证据结束已核实的零成交尝试，记录操作者、原因和前后状态。人工复核超时继续保留冻结；暂停新开仓时仍应允许查单和管理已知持仓。

## 5　Go 服务接口与可观测性

| 接口或数据 | 首版要求 |
| --- | --- |
| `POST /v1/order-intents` | 内部鉴权；接收稳定业务键、市场和标的、方向、预算或份额、价格边界、信号与截止时间。首次提交返回 201 和意图 ID，等价重试返回 200 与同一 ID，原始业务参数冲突返回 409。同步成功表示本地已受理 |
| `GET /v1/order-intents/{id}` | 返回意图、尝试与订单号、已确认量、未决量、最后对账、下一次检查和归属仓位。运营可发起“立即对账”，该操作只触发读请求 |
| Go 交易所适配器 | 分离准备签名、单次提交、查订单、按游标拉成交。为每次网络操作设置独立超时。固定市场版本、签名域、钱包模式与金额精度；用参考 SDK 测试向量验证签名及可推导的订单 ID |
| SQLite 持久化 | 意图、尝试、成交、持仓及资金预留共用一份账本，记录关键状态变化。`READY` 记录兼作待发送任务，未决记录供对账循环扫描。持仓可按已确认成交重算 |
| 指标与告警 | 记录重复意图命中数、同键冲突、未知订单数与最老年龄、受理至成交可见延迟、未归属成交、账实差额。建议初值：未知超过 30 秒提示，超过 5 分钟升级人工；发现同一开仓意图存在两张可能成交的订单立即报警。报警不解冻 |

## 6　单场比赛的查询与复盘

每项功能都以比赛 ID 为入口。首版先交付策略决策记录和赛后自动对账单，可以通过命令行或只读接口验收。实时面板和可配置的故障回放列为第二阶段。第 8 节的延迟成交回归用例仍随首版执行。

| 功能与优先级 | 使用场景与交付要求 | 验收示例 |
| --- | --- | --- |
| P0 策略决策记录 | 策略端记录比赛时钟、比分、策略版本、通道、信号标识与命中条件。Go 执行端补充当时的报价、成本、资金检查结果、跳过原因或订单意图 ID。按发生时间串联两端事件，保留首次触发、重复检查和最终处理的区别 | 按比赛 ID 和通道查询一次因价格越界而跳过的判断，能看到当时的报价、成本和阈值；查询已通过的判断，能定位到对应的开仓意图 |
| P0 赛后自动对账单 | 比赛结束自动按账户、比赛、通道生成报表，并列展示策略计划金额与数量口径、交易所逐笔成交、本地入账数量与成本。未归属订单单独列出。尚有迟到回报时标为“待核”，回报补齐后更新同一份报告并保留修订记录 | 注入 4 股和 6 股两笔模拟成交，本地只记入第一笔。报告须显示交易所共 10 股、本地 4 股、差额 6 股，并列出待核订单号。重复生成报告不产生新分录 |
| P1 实时比赛面板 | 比赛详情同时展示比分与比赛时钟、双方盘口、A/C/D 最近一次判断、未决订单及当前持仓。分别显示比分和盘口的最后更新时间，标明订单正在等待受理、成交确认还是对账 | 暂停比分源、继续推送盘口，再让一笔买单延迟确认。三种状态分别可见，值班人员能从面板进入该单的决策记录与订单时间线 |
| P1 按场故障回放 | 选择一场录制比赛，在指定事件注入回执丢失、成交延迟可见或进程重启，用可控时钟驱动模拟交易所。输出信号、外部订单数、成交与本地净持仓。数据集及故障参数可随问题单分享 | 两名开发者在独立数据库上重放双方选定的同一场比赛并使用相同的故障参数，得到相同的发单次数、成交量和净持仓。回放全程使用模拟账户与本地数据 |

## 7　启动与维护 SQLite

在仓库根目录运行 `go run ./cmd/executor`，默认只监听本机并使用模拟交易所。首次启动在可写数据目录创建 SQLite 文件、执行随程序提供的版本化迁移，空比赛列表即为正常就绪。后续启动复用同一文件，保留历史和未决订单；回放数据按需导入。实盘模式显式指定持久账本，正常重启如找不到原文件应停机排查，由专门的首次初始化步骤建立新实盘账本。开发启动、策略接入和查询命令见[运行说明](../README.md#启动-p0-执行服务)。

- **个人开发。** 每位贡献者需要 Git 和项目指定版本的 Go。仓库提供 SQLite 驱动依赖、迁移和示例配置，README 给出 Windows、macOS 和 Linux 的启动方式。运行生成的数据库、WAL、共享内存文件和凭证均留在个人环境中。模拟、测试和实盘使用不同的文件。
- **结构升级。** 表结构变更与对应 Go 改动一起提交。每个版本只执行一次迁移，失败时停止启动并保留故障信息。CI 在临时目录使用真实 SQLite 文件测试从空库初始化、从上一版带数据升级、重启恢复。备份和恢复须覆盖已提交的 WAL 内容，可使用 SQLite 的在线备份接口。[SQLite 备份说明](https://sqlite.org/backup.html)
- **扩容时机。** 增加比赛或本机策略进程时先复用同一执行服务，观察查询延迟和写入排队。若短事务优化后锁等待仍持续影响入场时限，或需要多台机器共同写账、自动接管同一账户，再评估 PostgreSQL、跨主机的发送权交接和故障恢复。SQLite 文件部署在本地磁盘；多机客户端通过服务接口访问。[SQLite 适用场景](https://sqlite.org/whentouse.html)

## 8　上线验收

以可控时钟、临时目录中的真实 SQLite 文件和能分别控制“接收、回执、撮合、成交可查询、余额可见”的模拟交易所验收。分别统计提交调用次数、交易所创建的不同订单数、本地分录数与净头寸。仅断言本地持仓行数会漏掉外部重复成交、本地少记持仓的故障。

| 场景 | 注入条件 | 必须观察到的结果 |
| --- | --- | --- |
| 01 同一信号重复触发 | 对任一比赛生成一次开仓意图；首单已受理，余额与成交隐藏 60 秒；第 16 秒后重复同一信号，再返回原单的成交明细 | 初始 POST 一次、外部订单一张、入场意图一个；等待期间资金仍冻结；最终入账量等于原单已确认成交量 |
| 02 回执丢失与崩溃 | 分别在标记发送后尚未发包、交易所受理后未写回执、写成交事务提交前后杀进程，再跨日重启 | 发包前崩溃允许零张订单；已受理的恢复后仍为一张；任何阶段已确认成交恰好记账一次 |
| 03 并发与接管 | 两个策略进程向同一个服务并发提交同一意图共 100 次，同时尝试启动第二个执行服务；另测同键改预算 | 相同请求返回同一 ID；改预算返回 409；第二个服务未获得账户独占锁即退出；最多一张可执行订单，预算和持仓名额只占一次 |
| 04 迟到与多笔回报 | 同单两条成交先后可见，分页查询重叠并重复返回每一笔，最后再到一条较早状态 | 每一明细恰好入账一次，量与加权均价正确，迟到状态不覆盖终态 |
| 05 同标的隔离 | A、C 与手工单买同一标的，回报交错；模拟卖单受理未回执，余额 30 秒后仍是旧值 | A/C 各自归账；手工成交单列待核；重复退出事件不触发第二次卖出，卖量不超本仓可卖份额 |
| 06 明确拒绝与证据不足 | 分别返回参数错误、可验证零成交的临时拒绝、超时、查单 404、读接口 5xx | 只有已证实零成交且在窗口内的可重试拒绝允许受限新尝试；其余按第 3 节决策表执行 |
| 07 风险额度与依赖中断 | 两场争用最后一个名额；注入 SQLite 锁忙或磁盘不可写、成交查询超时，恢复时重复返回相同明细 | 至多一场预留成功；无法持久化发送权时无新 POST；补拉后持仓与逐笔成交一致 |
| 08 历史双单差额 | 注入两个不同订单号，两者均成交，只有一个可归属本地意图 | 两笔外部成交均被发现，差额告警；多出的订单保留在待核队列，禁止用业务去重吞掉真实敞口 |

## 9　切换与回退

1. **离线验收。** 用固定 ESPN 和市场数据对齐 Python 信号，跑通上表。另用目标协议契约样本验证签名、成交最终性、错误分类、订单查询和回报关联。无法验证离线订单身份时，回执丢失的意图进入待核，保留资金预留。
2. **影子运行。** Python 维持现有执行，Go 接收相同的策略意图，模拟执行并只读对账。逐场比较比赛映射、通道、方向、价格和拟用预算；记录所有差异。验证 Go 影子实例对交易所的写请求数为零。
3. **切换单一写方。** 暂停该账户新入场，停用旧 runner 的交易权限，盘点开放订单、未决尝试、资金和仓位；按成交证据导入历史持仓与已用通道。无法归属的份额先隔离。只有 Go 接管后才开放该范围的新单；先小范围运行，确认无未解释差额，再扩大范围。
4. **回退。** 关闭 Go 新单入口，维持订单回报消费和对账。导出未决订单、已用通道和仓位。仅在原写方已失去发送权限、全部待接管状态可被接替方正确恢复后移交；否则保持只读对账。回退演练需证明同一账户在任何时刻只有一个有效写方。
